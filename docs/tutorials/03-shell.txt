If you spend any serious time inside the MongoDB Shell, you already know that typing out long diagnostic queries from scratch—especially during a live production incident—is a recipe for mistakes. Because mongosh is a full JavaScript runtime, you can turn your most common operational tasks into fast, reusable helpers. Today, we're walking through eight essential mongosh scripts every developer and DBA should keep in their toolkit—from guarding against accidental writes on a primary node, to auditing unused indexes, safely deleting millions of records, and cloning entire collections with their indexes intact. Let's jump right in.
First up is the environment-aware shell prompt. Before you run a single query, your shell should tell you exactly where you are. By default, mongosh gives you a fairly plain prompt, which makes it way too easy to think you're on a read-only secondary when you're actually connected to a production primary. By overriding the global prompt function inside your .mongoshrc.js file, mongosh will automatically execute this code every time the shell starts up. Here, we call db.hello() to inspect the replica set topology. If isWritablePrimary is true, the prompt prefixes your active database name with PRIMARY. If you're on a secondary or a standalone node, it labels that too—giving you an instant visual guardrail before you hit Enter on a write operation.
Second is finding and killing slow operations. Suppose production is spiking, CPU is pegged, and you need to find the runaway query causing the bottleneck right now. Instead of the older db.currentOp() helper, we want to run the $currentOp aggregation stage against the admin database so we can filter and project only what matters. We filter out idle connections and look strictly for active queries, updates, deletes, or commands running longer than five seconds. The projection hands you the namespace, the offending command shape, and most importantly, the operation ID. Once you spot the culprit, you just pass that ID into db.killOp() to terminate it cleanly.
Third is auditing unused indexes across a database. Indexes speed up reads, but every extra index slows down writes and eats up precious WiredTiger RAM. Over time, features get deprecated and old indexes get left behind. This script scans every non-system collection in your current database to find indexes pulling zero weight. Using the $indexStats stage, we look for indexes where operations equal zero—making sure we exclude the mandatory _id index. One quick tip before you drop anything: check the since timestamp in the output. Those counters reset whenever a node restarts, so make sure the server has been up long enough to cover your weekly or monthly reporting jobs.
Fourth is a collection storage and index overhead report. When disk usage starts creeping up or your working set no longer fits in memory, you need a bird's-eye view of where your bytes are going. This script builds a clean summary table comparing logical data size, compressed storage size on disk, and total index footprint in megabytes. Because mongosh supports standard Node.js console APIs, passing our sorted array into console.table() formats everything into crisp, aligned columns right in your terminal. If you see index megabytes dwarfing storage megabytes, that's a strong signal you're over-indexed on that collection.
Fifth is a dynamic schema and BSON type inspector. MongoDB's flexible document model is great for rapid iteration, until an application update accidentally starts saving user IDs as a plain string instead of an ObjectId—quietly breaking your queries and indexes. Since schemaless collections don't have a DESCRIBE TABLE command, we can build our own using $sample. This helper pulls a random sample of documents, inspects each field's underlying BSON type—distinguishing between ObjectId, Decimal128, arrays, nulls, and primitives—and tallies them up. If a field shows 980 ObjectId occurrences and 20 string occurrences, you've just uncovered a hidden data-hygiene bug in seconds.
Sixth is throttled batched deletes. Suppose you need to purge ten million expired log documents. If you fire off a single deleteMany() call, MongoDB will lock pages, thrash the WiredTiger cache, and potentially flood your oplog—causing your secondary nodes to fall behind in replication. Instead, we chunk the work into small, throttled batches. In each loop iteration, we grab just the _id values for one batch—which is super lightweight—delete those specific documents, print our progress, and call sleep() for a fraction of a second. That tiny breather gives replication and normal application traffic plenty of room to breathe while the cleanup runs safely in the background.
Seventh is checking replication lag and your oplog window. Speaking of replication health, whenever you're running heavy batch writes or troubleshooting failover readiness, you need to know two things: how far behind your secondaries are, and how much history your oplog can hold before a lagging node falls off and requires a full initial sync. Calling db.getReplicationInfo() calculates the exact time span between the oldest and newest entries in your oplog—say, 48 hours. Right below it, db.getSecondaryReplicationInfo() shows the exact timestamp and seconds of lag for every secondary member in the set, letting you verify cluster health in two lines.
Finally, eighth is replicating a collection with its indexes. What if you want to clone a collection inside the same database—maybe to test a risky schema migration or benchmark a new aggregation pipeline against real production data—without losing your secondary indexes? A simple $out aggregation copies all the documents fast on the server side, without streaming data back and forth through your client machine, but $out does not copy secondary indexes automatically. So we wrap $out and getIndexes() into a single helper function. First, $match with an empty filter pipes every document directly into $out, creating the target collection cleanly on the server. Next, if copying indexes is enabled, we read the source collection's index definitions via getIndexes(), strip out internal metadata, and pass the key pattern along with any custom options—like unique, sparse, or TTL expiration—straight into createIndex() on our new collection.
Drop any of these functions straight into your .mongoshrc.js file, and they'll be ready whenever you open a terminal. Thanks for watching, and happy querying!
